# 项目展示与简历说明

## 项目定位

本项目要证明的不是“会调用一个测试工具”，而是能够把接口测试中的执行、依赖、数据传递、
断言和安全边界做成可复用的工程能力。

当前第二阶段的核心展示点：

1. 运行级变量通过 `{{variable_name}}` 在路径、请求头、查询参数、JSON 请求体和断言中复用。
2. 前序 JSON 响应按路径提取数据，后续用例通过显式依赖形成业务链路。
3. 完整占位符保留整数、布尔值、列表等 JSON 类型，避免把所有测试数据错误地字符串化。
4. 缺失变量、提取失败、依赖失败和网络错误使用结构化状态与错误码表达。
5. 网络目标默认拒绝，本地演示也要显式开启；敏感变量不会在执行结果中返回其值。

## 面试现场演示顺序

演示前只使用仓库自带的本地接口和虚构数据，不连接真实业务或生产环境。

1. 展示 `contracts/test-run-v0.2.yaml`，说明先冻结跨模块契约再由多个 Agent 并行开发。
2. 不开启本地目标开关提交示例，展示默认拒绝的目标策略。
3. 在服务进程中设置 `ALLOW_LOCAL_TARGETS=true` 后重新启动。
4. 提交 `examples/demo-run.json`，解释第一个用例如何提取 `user_id`、`user_name`。
5. 展示第二个用例的 `depends_on`、路径模板、查询参数模板和断言模板。
6. 指出响应只包含 `extracted_variables` 名称，不包含提取值和请求头。
7. 运行全量 Pytest，并以现场输出说明测试数量和覆盖率。

启动与请求命令见仓库根目录 `README.md`。如果任何一步没有通过，应如实解释当前缺陷，
不要使用预先录制的成功结果替代验证。

## 简历表述模板

只有在相应功能已经由代码和测试验证后，才可使用以下表述：

> 设计并实现顺序接口自动化测试执行器，支持运行级变量、响应 JSON 路径提取、
> 显式用例依赖及路径/请求/断言模板化，覆盖缺失变量、提取失败和依赖跳过等失败路径。

> 为测试目标加入默认拒绝的 origin 白名单策略和显式本地开发开关，关闭重定向及环境代理继承，
> 并对秘密变量、请求头和网络异常进行集中脱敏，降低 SSRF 与敏感信息泄漏风险。

> 基于 FastAPI、httpx、Pydantic 和 Pytest 构建可复现的接口测试服务，通过结构化结果输出
> 用例状态、错误码和执行汇总。

可以在验证后补充真实指标，例如：

- 自动化用例数量：以 `pytest` 输出为准；
- 代码覆盖率：以 `pytest --cov=app` 输出为准；
- 示例业务链路数量和接口数量：以仓库实际内容为准；
- 已验证的边界场景：以测试名称和测试代码为依据。

不要填写估算数字，也不要声称已经具备尚在路线图中的数据库、Allure、OpenAPI 导入、
CI/CD、Docker、Web 前端或大模型能力。

## 面试追问准备

### 为什么采用顺序执行而不是 DAG 并发？

当前目标是确定性表达登录、提取令牌、查询资源等线性业务链路。顺序执行更容易保证变量发布
时机和失败语义；DAG 调度、并发隔离和资源控制属于后续范围。

### 为什么依赖和变量引用要同时存在？

`depends_on` 表达业务语义和失败传播；模板引用负责数据传递。只依靠变量是否存在，无法清晰表达
一个用例为什么应被跳过，也不利于生成可读报告。

### 为什么提取要原子发布？

如果多个提取规则只成功一部分就写入运行上下文，后续用例可能使用半完整状态。只有断言和所有
提取规则都通过后统一发布，可以保证后续读取到一致的数据。

### AI 在项目里扮演什么角色？

当前版本的结果判定完全由确定性断言完成。未来 AI 可以辅助生成边界场景或总结失败日志，
但生成内容必须经过规则校验和人工确认，不能让模型直接决定测试是否通过。

## 诚实展示边界

- 当前 API 无认证，只用于可信本地开发，不对公网开放。
- 当前目标策略按配置的 origin 和本地主机名判断，不等同于完整的企业级网络隔离。
- 当前只支持 JSON 响应提取和点分隔路径，不支持 JSONPath 全语法。
- 当前用例按提交顺序串行执行，不提供任务队列、历史持久化或并发调度。
- 项目指标必须来自当前提交对应的测试输出，不能沿用旧版本数字。
