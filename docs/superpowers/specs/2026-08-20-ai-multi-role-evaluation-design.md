# 多角色 AI 候选与测试草稿评测设计

## 状态

已获用户确认，进入实现准备阶段。

## 背景

当前平台已经有一个 AI 生成角色：它读取脱敏后的 OpenAPI 结构，生成边界、异常和健壮性候选用例，并把结果交给人工审核。当前 Provider 默认为 Mock，代码已经支持通过同一 Provider 切换到 OpenAI。

本次扩展不引入三个不同模型，而是在同一个 Provider/模型上增加两个逻辑角色：候选评测角色和测试草稿评测角色。角色之间通过不同的任务提示词、输入摘要和严格 JSON 输出契约隔离，效果类似应用内部的子 Agent。

## 目标

- 候选生成完成后，由候选评测角色给出独立的质量反馈。
- 候选加入当前测试草稿后，用户可以手动触发草稿评测。
- 用户人工修改草稿后，可以再次触发评测；旧反馈必须显示为过期。
- 用一个独立、可展开的 AI 反馈窗口查看候选评测或草稿评测。
- 评测只读，不自动修改、不自动执行、不影响最终确定性测试判定。
- Mock 模式可以离线完成完整演示，真实 Provider 仍只从未提交环境变量读取密钥。

## 非目标

- 不接入 Codex 运行时子 Agent作为生产依赖。
- 不为每个角色配置不同模型；后续可扩展，但不是 v0.1 的要求。
- 不把 AI 反馈写入历史运行数据库。
- 不把评测结果当作测试通过/失败结果。

## 方案选择

### 方案 A：同一 Provider 的逻辑角色编排（推荐）

保留现有生成接口，新增两个评测接口。每个角色使用独立的安全输入摘要、系统指令和 Pydantic 输出模型；Mock Provider 返回确定性评测，OpenAI Provider 使用同一 Responses API 和当前模型完成角色调用。

优点是改动边界清晰、评测可以单独重试、每个角色的输出可验证，也能在未来把某个角色切换到不同模型。代价是生成后至少增加一次 AI 请求，真实 Provider 会增加费用。

### 方案 B：一次请求同时生成和评测

让生成 AI 在一次响应里返回候选和自评结果。延迟和请求次数较低，但生成者评估自己容易产生共同偏差，评测失败会连带候选生成失败，也不利于之后独立替换评测模型。

### 方案 C：不同模型分别承担角色

为生成、候选评测和草稿评测分别配置模型。独立性最好，但增加配置、费用、超时、Provider 状态和故障组合；当前用户需求没有要求，不作为第一版实现。

本次采用方案 A。

## 角色与数据流

```text
OpenAPI 文档
    │
    ├── 现有生成角色 ──> 候选用例 + 生成理由
    │                         │
    │                         └── 候选评测角色 ──> 候选质量反馈
    │
    └── 人工选择/编辑 ──> 当前测试草稿
                                  │
                                  └── 点击“AI 评测当前草稿”
                                          └── 草稿评测角色 ──> 草稿质量反馈
```

候选评测在生成成功后自动触发，但评测失败不丢弃候选；用户仍可继续人工审核。草稿评测不监听每次键盘输入，只由按钮触发，避免编辑过程中产生大量请求和费用。草稿发生变化后，之前的反馈标记为过期。

## 后端接口

### `POST /api/v1/ai/cases/evaluate`

输入包括脱敏 OpenAPI 文档、候选运行配置、候选生成理由和可选测试目标。服务端只把结构化摘要交给 Provider，不发送 base URL、认证信息、请求头值、变量值或请求体敏感值。

返回统一的评测反馈：Provider、模型、0～100 分、摘要、优点、问题、建议、评测用例数量和 `requires_human_review=true`。每个问题可带 `case_id`，严重级别为 `info`、`warning` 或 `error`。

### `POST /api/v1/ai/drafts/evaluate`

输入包括当前草稿和可选 OpenAPI 文档。服务端按同样规则制作脱敏结构摘要，重点保留方法、相对路径、参数结构、断言类型/路径、依赖和提取元数据，不保留真实值。

返回格式与候选评测一致，但 `role` 为 `draft_evaluator`。反馈只描述问题和建议，不返回替换后的测试用例，避免用户误以为 AI 修改已经被应用。

两个接口共享 Provider 配置和错误码体系。OpenAI 请求使用独立角色指令和严格 JSON Schema；Mock Provider 使用确定性规则，确保没有 API Key 时也能测试前端流程。

## 前端交互

- AI 生成区域沿用现有“生成 AI 候选”，生成成功后后台触发候选评测。
- 生成区域显示评测状态，并提供“重新评测候选”按钮。
- 测试配置区域增加“AI 评测当前草稿”按钮。候选替换或追加到草稿后按钮可用；人工修改 JSON 或候选字段后反馈变为“草稿已变更，需重新评测”。
- 增加一个页面内 `dialog` 作为 AI 反馈窗口，包含当前反馈范围、评分、摘要、优点、问题和建议。它不是新的浏览器弹窗，桌面端以独立浮层展示，移动端占满屏幕。
- 候选反馈和草稿反馈在同一个窗口内切换，始终标明角色和生成时间/状态。
- 反馈窗口中的所有内容使用安全 DOM 文本节点渲染；AI 返回不可信文本，不能使用 `innerHTML`。
- 评测按钮不会改变运行按钮状态，也不会调用 `/api/v1/runs`。

## 错误处理与安全

- Provider 未配置、网络失败和结构化输出无效分别返回现有 503/502 错误语义；前端显示可读错误，但保留已有候选或草稿。
- 输入不符合 `TestRunRequest`、OpenAPI 过大或脱敏摘要超限时返回 422。
- 服务端对评测输出执行 Pydantic 严格校验：分数范围、问题数量、文本长度、严重级别和 case ID 都必须合法。
- 任何评测输入都先经过脱敏和结构摘要；绝对 URL、凭据、请求头值、变量值和原始请求体值不得进入 Provider。
- 评测结果仅保存在当前页面内存，不进入运行历史，不影响测试报告。

## 测试策略

- Provider 单元测试：Mock 生成三类评测结果；OpenAI 结构化响应解析、超限、错误和非法输出。
- 安全测试：评测输入不包含 base URL、凭据、变量值、请求头值和敏感 body 值。
- API 测试：两个新接口的成功、422、502、503 和评测失败不丢候选行为。
- 前端契约测试：反馈窗口 DOM、候选自动评测、草稿按钮、草稿变化后的过期状态、错误保留候选。
- 回归测试：现有生成、候选审核、运行和历史流程不改变。

## 后续可扩展项

- 按角色分别选择模型/Provider。
- 保存评测快照并与历史运行报告关联。
- 支持人工采纳单条建议并生成变更预览，而不是直接修改草稿。
- 候选评测和草稿评测的异步队列化。
