# ai-multi-role-evaluation — 多角色 AI 候选与草稿评测

状态：IMPLEMENT

## 目标

在现有 AI 候选生成能力之上增加两个只读评测角色：候选用例评测和测试草稿评测。
评测结果通过一个独立的 AI 反馈窗口展示；人工仍然是唯一的修改和执行决策者。

## 范围

- 复用现有 AI Provider 和模型配置，按逻辑角色使用不同提示词及结构化输出。
- 候选生成完成后自动触发候选评测，并支持手动重新评测。
- 候选加入测试草稿后，提供“AI 评测当前草稿”按钮。
- 草稿被人工修改后，将已有草稿评测标记为过期，允许再次评测。
- 增加候选评测和草稿评测 API、Mock 实现、OpenAI 实现及前端反馈窗口。
- 保持评测只读、脱敏、无自动执行和无自动修改。

## 非范围

- 不接入三个不同模型或三个不同外部 Provider。
- 不让评测 AI 自动修改候选或测试草稿。
- 不让 AI 直接执行被测接口或参与最终通过/失败判定。
- 不在本阶段持久化 AI 反馈，不新增 MySQL 表。
- 不把 Codex 运行时子 Agent 作为生产服务依赖。
- 不改变现有 `/api/v1/ai/cases/generate` 契约。

## 验收标准

- [ ] 现有生成 AI 流程保持兼容，生成结果仍要求人工审核。
- [ ] 候选评测能返回整体评分、摘要、优点、问题和建议，并能关联候选 ID。
- [ ] 草稿评测能评估当前编辑器草稿，并能关联用例 ID或给出全局问题。
- [ ] 评测结果严格通过 Pydantic/前端契约校验，异常输出不会进入反馈窗口。
- [ ] 评测输入不包含 base URL、请求头值、请求体敏感值、变量值或 API Key。
- [ ] 候选生成成功但候选评测失败时，候选仍可人工审核，页面明确提示评测失败。
- [ ] 草稿变更后旧反馈标记为过期，必须重新点击评测才能更新。
- [ ] 评测按钮不会触发测试执行；运行测试仍需单独点击。
- [ ] Mock Provider 在无 API Key 时可完成完整演示；OpenAI Provider 只从未提交 `.env` 读取密钥。
- [ ] 后端、前端契约和安全回归测试通过。

## 风险与假设

- 同一模型承担生成和评测角色时可能存在共同偏差；本阶段通过不同提示词、独立请求和结构化评测输出降低耦合，后续再支持按角色配置模型。
- 真实 Provider 评测会增加 API 调用次数和费用；Mock 评测用于本地开发和回归测试。
- 评测需要理解测试结构但不能接收凭据，因此输入采用结构化、脱敏摘要，可能牺牲部分业务语义。
- 页面刷新后反馈丢失，与现有候选审核的页面内存模型一致。
